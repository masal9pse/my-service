# ADR-0001: 単一コンテナによるフロントエンド (React SPA) とバックエンド (Go) の同居配信の採用

* **ステータス**: 承認済み (Accepted)
* **作成日**: 2026-10-11
* **決定者**: プロジェクトオーナー
* **関連ドキュメント**: [ARCHITECTURE.md](../../ARCHITECTURE.md)

---

## 1. コンテキスト (Context & Problem Statement)

StrandLog (My Portfolio) アプリケーションの開発において、フロントエンド（React 19 + TypeScript + Vite）とバックエンド（Go 1.22 + Supabase）のホスティングアーキテクチャおよび CI/CD パイプラインの構成方針を決定する必要がありました。

主な課題として以下の点が挙げられます：
1. **初期フェーズにおけるインフラコストと運用工数を最小限に抑えたい**。
2. **フロントエンドとバックエンドを別々のサービス（例: Vercel + Cloud Run）に分離すべきか、単一のコンテナ（Cloud Run）にまとめるべきか**。

---

## 2. 検討した選択肢 (Considered Options)

### 選択肢 1: Go バックエンドによる単一コンテナ同居配信 (採用案)
* **概要**: マルチステージ Dockerfile により、React のビルド成果物（`frontend/dist`）を Go サーバーのコンテナに同梱し、Cloud Run 上で Go が静的配信（SPA ハンドラー）と REST API の両方を提供する。
* **メリット**:
  * インフラが Cloud Run 1 サービスで完結し、管理が極めてシンプル。
  * 同一オリジン（`/` が SPA、`/api/...` が API）となるため、CORS エラーや Cookie/認証のクロスオリジン問題が発生しない。
  * フロントとバックエンドのバージョン不整合（API互換性の崩れ）が起きない。
* **デメリット**:
  * フロントエンドのわずかな修正（CSS や文言）であっても、Cloud Build で Go のビルドが連動して実行され、デプロイに 3〜5 分の待ち時間が発生する。
  * バックエンド側の設定不備（依存関係エラー等）でフロントエンドのデプロイが巻き込まれて失敗するリスクがある。

### 選択肢 2: フロントエンドとバックエンドの完全分離
* **概要**: フロントエンドを Vercel や Cloudflare Pages にホスティングし、バックエンドのみを Cloud Run で API サーバーとして運用する。
* **メリット**:
  * フロントエンド単体のデプロイが極めて高速（30 秒〜1 分程度で完了）。
  * バックエンドのビルドエラーにフロントエンドが巻き込まれない。
  * エッジ CDN による高速な静的アセット配信の恩恵を受けられる。
* **デメリット**:
  * 管理すべきインフラ（ホスティングサービス、ダッシュボード、設定）が 2 つに増える。
  * CORS の設定管理や環境変数（API エンドポイント URL）の管理が必要となる。

---

## 3. 決定内容 (Decision)

現行の初期・ポートフォリオフェーズにおいては、**「選択肢 1: Go バックエンドによる単一コンテナ同居配信」を採用する**。

### 決定理由
1. **YAGNI 原則（早すぎる最適化の回避）**:
   現フェーズでは機能開発と完成度の向上が最優先であり、インフラの分散による管理工数の増加を避ける。
2. **強力な無料枠によるコスト 0 円の成立**:
   Cloud Build の無料利用枠が非常に大きく、個人開発の範囲内であれば毎日のデプロイを繰り返しても完全無料（0 円）で運用可能である（下記エビデンス参照）。
3. **CORS / オリジン間問題の完全排除**:
   同一コンテナ・同一ポート（8080）で動作するため、ネットワーク起因のトラブルが発生しない。

---

## 4. 受け入れたトレードオフ (Consequences)

本決定に伴い、以下のデメリットを許容（トレードオフとして受容）します：
* フロントエンド修正時にも Go のビルドが走り、毎回 3〜5 分の CI/CD 待ち時間が発生すること。
* バックエンドの設定エラー時にフロントエンドのデプロイも連動して止まる可能性があること（早期検知として受容）。

---

## 5. 見直し・移行の判断基準 (Criteria to Revisit)

以下のいずれかのトリガーが発生した段階で、本意思決定を見直し、「選択肢 2（フロントエンドの Vercel / Cloudflare Pages への分離）」への移行を実施します：

1. **コストトリガー（CI/CD の課金発生）**:
   Cloud Build の無料枠（月間 2,500 ビルド分）を超過し、毎月の費用請求が発生し始めたとき。
2. **DX トリガー（開発待ち時間のボトルネック化）**:
   フロントエンドの UI 試行錯誤や更新頻度が増加し、毎回 3〜5 分の CI ビルド待ち時間が開発効率の重大な阻害要因となったとき。
